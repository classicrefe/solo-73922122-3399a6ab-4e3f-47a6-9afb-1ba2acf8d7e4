# 提花色格 · 双工位协同改色台

两位织样师各用一个工位（A / B），在浏览器里同时修改同一张内置 24×24 提花色格图：
按住拖过若干格子，抬手即**整笔多格一起改色**。Node.js 服务端通过 WebSocket 同步，
交叠格按**服务端首次收下各笔的顺序叠色**；每人可撤销/恢复自己的任意一笔，
撤销露出下层仍有效的颜色，恢复回到原来的叠放位置。支持断线续画与重连按序补交。

## 快速开始

### Docker Compose（演示页推荐）

```bash
docker compose up --build
# 浏览器打开 http://localhost:8080
# 两个标签页分别选择工位 A、工位 B（或直接访问 ?station=A / ?station=B）
```

### 直接用 Node 运行

```bash
npm install
npm start            # 默认 8080 端口，可用 PORT 覆盖
# 打开 http://localhost:8080
```

### 测试与冒烟

```bash
npm test                       # 25 项：引擎单元 + 会话发闸单元 + 真实 WebSocket 双客户端集成测试
node scripts/smoke.js          # 对已运行的服务端跑 18 项线协议冒烟（默认 8080）
```

## 功能与规则对照

| 需求 | 实现 |
| --- | --- |
| 同一张内置提花色格图 | `shared/pattern.js` 纯函数生成 24×24 底图与色盘，浏览器和服务端共用同一份 |
| 两个工位 | 连接先 `hello` 选择 A/B；同工位新连接顶掉旧连接（4002），状态以服务端连接身份为准 |
| 拖一笔给多格改色、整笔一起生效 | 前端 pointer 事件收集去重格子，抬手笔生成一个 `paint` 操作；服务端一次 `applyOp` 整体受理 |
| 交叠格按服务端首次收下顺序叠色 | 每笔受理时分配全局单调 `seq`，每格维护按 seq 升序的叠层，最上层有效笔决定显示色 |
| 撤销/恢复自己的任意一笔 | 只切换 paint 的 `active` 标志，**不改变 seq 层位**；撤销露出下层，恢复回到原叠放位置 |
| 断线可继续画/撤销/恢复 | 操作先进本机 `pending` 队列并乐观渲染，无需在线 |
| 重连按本机顺序补交 | 重连发 `hello` 后进入“关闸”：收到全量 snapshot 并对账完成前，任何操作（含断线遗留与等快照期间新产生的）只排队不发线；开闸后 `_flush` 严格按本机 `clientSeq` 顺序补交，新操作不会插到旧待交操作前面 |
| 手动重发不能插队 | “重发待确认”重置发送标记后仍走同一个按序 `_flush` 队列，从头扫描，后产生的操作无法先到服务端 |
| 回执先于笔迹更新不回退 | `ack` 只把待确认项标记为已回执、**不出队**，乐观视图继续包含该笔；直到携带完整记录的广播 `op` 到达才移除，重绘不会闪回旧色 |
| 补交途中再次断线 | 断连即关闸并清空本连接的发送标记；重连快照里已有的操作不重发（服务端 id 去重保证只生效一次），其余按原顺序接着补交 |
| 应答丢失可重发、已收只生效一次 | 每笔带全局唯一 id；服务端 `allOpIds` 去重，重复 id 返回 `duplicate` 错误，绝不二次生效；页面有“重发待确认”按钮 |
| 补交完两边看到同一张图 | 服务端单一事实源 + 全量快照对账；集成测试断言两端 seq、操作集合与各色格显示完全一致 |

## 目录结构

```
shared/
  pattern.js   内置底图、色盘（浏览器/Node 共用 UMD）
  engine.js    纯函数状态引擎：校验、按 seq 叠色、撤销/恢复翻标志位、快照序列化
  session.js   客户端同步会话：pending 队列、乐观视图、快照对账、发闸与按序补交、ack 不出队
server/
  server.js    内置 http 静态服务 + ws WebSocket；按到达顺序受理、id 去重、广播
  test/        node:test 单元测试与集成测试
public/        演示页面（画布拖笔、色盘、笔迹面板、连接/待确认状态）
scripts/
  smoke.js     原始 WebSocket 报文级冒烟脚本
Dockerfile / docker-compose.yml   容器化演示（含 /healthz 健康检查）
```

## 协议摘要

- 客户端 → 服务端：`hello`（选工位）、`op`（提交操作）、`resync`（重拉快照）
- 服务端 → 客户端：`snapshot`（全量状态）、`ack`（受理确认）、`op`（广播含全局 seq）、
  `error`（含 `duplicate` 标志）、`presence`（在线工位数）
- 操作对象：`{ id, type: 'paint'|'undo'|'redo', author, color?, cells?, paintId?, clientSeq }`

## 本次修复的缺陷（重连过程）

1. **重连补交乱序**：旧实现里 `attach` 后立即在线，等快照期间新产生的操作会被立刻发出，
   而断线遗留操作要等快照对账后才补交——同格两笔因此按“新笔在前、旧笔在后”受理，
   交叠格最终显示先刷的赭金而非后刷的绛红。修复：引入连接级发闸（`gateOpen`），
   快照对账完成前所有业务操作只入 `pending`；开闸后 `_flush` 按本机 `clientSeq` 统一按序补交，
   手动重发复用同一队列，无法插队。
2. **回执先到导致本地回退**：旧实现收到 `ack` 就把操作移出 `pending`，若广播 `op` 尚未到达，
   下一帧重绘只剩确认态，乐观颜色闪回旧色。修复：`ack` 仅打 `_acked` 标记不出队，
   直到携带完整记录的广播 `op` 到达才移除并由确认态接管。

## 待完成 / 已知边界

- 本环境未安装 Docker，compose 文件按标准结构人工复核，未在本机实际 `docker compose up`；
  在有 Docker 的机器上可直接构建运行。
- 状态保存在内存，服务端重启后操作历史清空（演示用途）；持久化（SQLite/日志）未做。
- 未做用户认证，工位身份靠自选；同工位互踢仅适合同一台演示机双标签场景。
- 撤销/恢复目标笔不存在、重复切换等情况服务端会拒绝并提示；客户端按钮按当前状态置灰逻辑
  依赖快照延迟，极端并发下以服务端裁决为准。
- 无操作级游标/选区协同与编辑锁；当前模型为“最后受理者在上层”的叠色语义，无冲突弹窗。
